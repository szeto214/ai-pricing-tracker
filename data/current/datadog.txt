Common Questions
Definitions
How do you define retention?
The retention period is the number of days your logs are searchable and analyzable. After this period, logs disappear from your index(es).
Logs removed from your index(es) do not have to be gone forever! Check out our
Log Archives
for long-term storage options.
I know my consumption in GB/day: how do I convert it into millions of log events?
Log events come in all shapes and sizes, which is precisely why we offer event-based pricing! We want to encourage rich logs to provide the most value.
The best way to get the number of log events during your Datadog trial is to run a count query over the last 24 hours and multiply by 30 days to estimate for the month. This can, of course, also be done in your current log management solution, if you have one.
What do the different compute sizes in Flex Logs mean? Which one is appropriate for me?
Compute is the querying capacity to run queries for Flex Logs. The compute size appropriate for you depends on the volume of data stored in the Flex Tier, the time window and complexity of your queries, and concurrency. For guidance on which compute size you should choose, see our
documentation
.
Supported Today
Can I subscribe to Log Management without using Datadog Infrastructure or APM?
Having all your infrastructure, APM, and log data under one roof is something we definitely encourage, but you can also subscribe only to Datadog’s Log Management. Learn how to configure only log collection
here
.
What retentions are available for on-demand customers?
For on-demand customers, the default retention is 15 days. If you have already created a Datadog account and would like to use a different retention, you can request a different retention at
support@datadoghq.com
Do I have to choose only one type of retention between Standard Indexing and Flex Logs?
Your indexes can have Standard Tier retention only, Flex Tier retention only, or a combination of Standard and Flex Tier.
What is the difference between Standard Indexing and Flex Logs?
Flex Logs does not support monitors or Watchdog Insights. Standard Indexing supports everything.
What happens if I send an unexpectedly high volume of logs?
By committing to a monthly volume of logs, you aren’t rate-limited based on a single day’s volume. Send as much as you need on any given day without losing visibility. Assuming your average is lower on other days, your bill is unaffected.
In those cases where you have a big month, not to worry! You maintain complete visibility and pay for additional services (+50% of the annual price) only on the volume that exceeds your commitment.
Can I forward logs from one Datadog account to another?
This is currently not supported.

When should I store logs in Standard Indexing vs Flex Logs?
Log events can be stored in Standard Indexing when you need them for real-time troubleshooting and in Flex Logs for ad-hoc, historical analysis and long term troubleshooting. See our

A feature flag lets you enable, disable, or configure application behavior without redeploying code. Teams use feature flags to safely release features, run canary rollouts, and validate changes using real production traffic.

Do Feature Flags require APM?
Feature Flags can be used independently and don’t require licensing other Datadog products, but they leverage the APM and RUM SDKs for server-side and client-side implementations.
Can I investigate feature flag impact in APM, RUM, and Product Analytics?
Yes, but you must already be a customer of the relevant Datadog products. Feature flag evaluations are automatically correlated with Datadog APM, RUM, and Product Analytics data, allowing you to investigate errors, performance issues, and user behavior tied to specific flag states.
Can I migrate from another feature flag provider?
Yes. Datadog Feature Flags is built on the OpenFeature standard, which helps teams avoid vendor lock-in and simplifies migrations from existing providers. OpenFeature is a CNCF (Cloud Native Computing Foundation) project backed by major industry leaders, ensuring long-term portability and ecosystem support.
How reliable are Datadog Feature Flags?
Feature flag evaluations are designed to be highly reliable and safe by default. Datadog uses a globally distributed CDN-backed architecture to ensure low-latency access and resilience at scale. SDKs cache flag values locally and fall back to safe defaults if connectivity is interrupted, ensuring your application continues to operate even during network or service disruptions.
Which SDK languages are supported?
Datadog Feature Flags supports SDKs for common backend and frontend languages, including Java, JavaScript, Python, React, Go, Ruby, and mobile platforms.

Common Questions
How do you define a host?
A host is any physical or virtual OS instance that you monitor with Datadog. It could be a server, VM, or node (in the case of Kubernetes).
How do I monitor containers?
The Datadog Agent runs in a container alongside any number of other containers on a host. From there it can collect metrics from its neighboring containers and from the host itself. Depending on your plan, you can monitor 5 or 10 containers free for each host license. Additional containers will be billed at $
0.002
per container per hour. In addition, you can purchase prepaid containers at $
1
per container per month or $
1.50
per container per month for DevSecOps Containers.
What is a custom metric?
Datadog was designed to allow you to monitor your own custom applications and business metrics—not just your infrastructure. You can send any and all of your organization’s important metrics to Datadog for graphing, alerting, correlation, anomaly detection and more. Example uses: monitoring ad revenue, the rate at which shopping carts are abandoned, or the health of an in-game economy. Many customers find these metrics invaluable, especially when combined with infrastructure metrics.
How many custom metrics are
allotted
per host?
Datadog offers 100 custom metrics for every host monitored with Infrastructure Pro, or 200 custom metrics for every host monitored with Infrastructure Enterprise.
How do I get charged for additional custom metrics?

How does Datadog count and meter custom metrics?
Custom metrics are counted hourly and averaged monthly across your entire account, not on a per-host basis. For more details around Custom Metrics metering, please see our
Custom Metrics Billing FAQ
.
What is a custom event?
Datadog allows you to send custom events coming from your own custom applications such as custom-built deployment tools or scheduled maintenance jobs. This way, you can correlate any of these events with performance metrics, create monitors for alerting and enrich events at intake with processing pipelines to be queried alongside other standard events.
How many events are
allotted
per host?
Datadog offers 500 custom events for every host monitored with infrastructure monitoring for pro plan, or 1000 for enterprise plan. Custom events are averaged across your entire account, not just on a per-host basis. Beyond this limit, Datadog charges $
2
for 100 000 custom events (billed annually or $
3
on-demand), although it is rare for our customers to exceed the allotted volume.
How can I send custom metrics and events?
You can send Datadog custom metrics and events in three ways
The Datadog Agent ships with DogStatsD so you can submit custom metrics via the Agent's non-blocking API functions for many programming languages.
The Datadog Agent allows for the creation of custom integrations via plugins to the Agent. This plugin system allows the Agent to collect custom metrics on your behalf. Integrations which are contributed back to the Datadog Agent convert to standard metrics.
Datadog also has a full-featured API that you can send your metrics to—either directly over HTTP or with a language-specific library.

more

is our top priority. This includes, universal HTTPS, strong TLS configuration, and HTTP Strict Transport Security. Our Agent is open-source, which means it can be reviewed to ensure it meets your security requirements.

What is Continuous Testing?
Datadog
Continuous Testing
is a comprehensive toolkit in the development cycle that offers integration and end-to-end testing with codeless test setup, self-healing capability, and seamless integration with CI providers (GitHub Actions, Azure DevOps, CircleCI, GitLab, and Jenkins) and collaboration tools to help you ship high-quality features to your users quickly.
Running tests in your CI/CD pipelines today is included with your API and Browser Testing test runs, and tests will run sequentially (one after another). If you would like to increase the speed of testing in your CI/CD pipelines, you can purchase additional Parallel Testing speed (parallelization), which makes some tests run at the same time.
For example, 1 Parallel Testing additional speed offers an additional parallel slot, allowing you to run 2 tests in parallel; 2 Parallel Testing additional speed offers 2 additional parallel slots, allowing you to run 3 tests in parallel; and so on. This helps you run more tests in parallel (at the same time), and reduce the overall execution speed of your test suite.
Am I limited to a certain number of test runs based on my additional parallelization?
No. With Parallel Testing, you can run as many tests as you need in your CI/CD pipelines. Parallelization ensures you can run more of those tests at the same time, and ultimately reduce the duration of testing in your CI/CD pipelines.
For example, if you want to run 100 tests in a CI pipeline and each test takes 10 seconds to run:
WITHOUT parallelization, your tests will run sequentially and your pipeline will take roughly
17 minutes to complete.
WITH parallelization, if you purchase (for example) an additional speed of 4 Parallel Testing, your 100 tests will run over a total of 5 parallel slots, and your pipeline will now take roughly
3 minutes to complete.
Note:
In both cases, your 100 test runs will contribute to your API or Browser Testing test run quotas.
Can I reuse my Synthetic tests that I use to monitor my production environments?
Yes. With Parallel Testing, you can use the same Synthetic tests you have configured for production monitoring across all of your staging, QA, and pre-production environments. Through variable overrides and custom configuration values, you can benefit from one test throughout your entire software development lifecycle.
What are parallel tests?
Parallel tests are tests that run simultaneously in your continuous integration and delivery pipelines to ensure that you can:
Reduce pipeline duration and ship new features faster
Increase development confidence and speed of delivery
Have complete test coverage and reduce the volume of production-breaking bugs from reaching your codebase
As an example, if you needed to run 60 tests and each test took one minute to run, it would take you one hour to run those tests sequentially. However, running those tests in parallel with a parallelization value of 60, you could run all your tests at the same time and within one minute, saving you 59 minutes to tackle other business-critical tasks. That's the power of Parallel Testing.

.
What counts as a browser test run?
Each simulation of a web transaction (up to 25 steps) counts as a single browser test run. A single test containing 50 steps would count as two test runs on each execution. For example, running a 60-step test (three test runs) every 15 minutes from five different locations and two different devices equates to 120 test runs in one hour.
How do subtests count toward billing?
Subtests are simply a set of steps within a browser test. Therefore, we count a subtest as part of the overall browser test execution. What counts as a “session” in Product Analytics pricing?
Similar to Real User Monitoring,
a session
is a continuous period of user interaction on your website or app, typically grouped by user activity and timeout thresholds. A session is a user journey on your web application. It expires after 15 minutes of inactivity and lasts up to 4 hours. For a detailed explanation of user sessions, please see our
docs
.
Is Product Analytics available for both Browser and Mobile Applications?
Yes – Product Analytics is available for Browser and Mobile Applications.
Can I use Product Analytics without enabling Session Replay?
Yes—Product Analytics works independently, allowing you to analyze conversion, retention, and workflow metrics without recording visual replays. That said, pairing it with Session Replay gives you powerful visual context to see exactly why users drop off or struggle, making it easier to validate hypotheses and troubleshoot faster.
How long is my data retained?
Behavioral data in Product Analytics is retained for a minimum of 15 months, so you can analyze long-term adoption and validate the lasting impact of product changes over time. By default, Session Replays will be retained for 30 days.
Can I get more than 15 months retention?
Yes – please reach out to your dedicated Datadog account team for more information.
How is Product Analytics different from Real User Monitoring?
RUM focuses on frontend performance—like load times and errors—while Product Analytics measures user behavior, including conversions, drop-offs, and feature adoption. Both use the same SDKs, but Product Analytics includes 15-month retention for behavioral data. They can be used separately or together for a complete view.
Does purchasing Product Analytics increase the retention period for Session Replays compared to RUM alone?
No — Session Replays have a standard 30-day retention period whether accessed through RUM or Product Analytics. If you’re interested in extending your replay retention, please reach out to your Datadog account team to discuss available options.
Will I get double-billed on Session Replays if I purchase both RUM and Product Analytics?
No — Session Replays are only billed once, even if you’re using them across both RUM and Product Analytics.
Is Product Analytics available in all regions?
Product Analytics is available for all US-hosted and EU-hosted Datadog accounts. It is not yet supported on GovCloud, but we’re actively working toward future availability.

Do I need Product Analytics to use Experiments?

RUM

Product Analytics
alongside Experiments can measure performance and behavioral impact alongside their business metrics.
How is this different from traditional A/B testing tools?
Datadog Experiments lets you measure the signals that matter — starting with business metrics directly from your native data warehouse. Can I monitor performance impact during experiments?

Functions inside Container Apps are counted as container replicas

Common Questions
What is Datadog Agent Observability and how does it work?
Datadog Agent Observability helps engineering teams evaluate, improve, and trace AI agents across development and production in one platform. It connects offline experimentation — datasets, experiments, evaluators, and human review — with production observability, including end-to-end agent tracing, quality monitoring, security scanning, and full-stack correlation with backend services and real user sessions.
What is an LLM span, and how is it different from other spans?
An LLM span is a single call to an LLM provider such as OpenAI or Anthropic. One agent workflow can generate multiple LLM spans — for example, a retrieval step, a reasoning call, and a tool-use call are each tracked as separate LLM spans within the same trace. Datadog bills only on LLM spans, not on tool spans, retrieval spans, or other workflow spans surrounding the model call. This means you pay for the actual AI work, not every step the agent takes to orchestrate it.

Is Sensitive Data Scanner (SDS) included in Agent Observability?
Yes. Sensitive Data Scanner is built into Agent Observability at no additional cost. For every 10K LLM spans, you receive an allotment of 1 GB of SDS processing. Agent Observability automatically scans, identifies, and redacts sensitive information — including personal data, financial records, and health information — from your LLM application inputs and outputs, helping prevent data leakage before it reaches users.
How does the Experiments feature work, and is it available to all customers?
Experiments are included in Agent Observability. You can build versioned datasets from real production traces, run experiments to compare prompts, models, tools, or agent logic side by side, and track results in the Datadog UI or via the SDK. Online evaluations run automatically in production to catch regressions as they happen. Offline, you run structured experiments against curated datasets before deploying. Together they give you confidence that your application performs reliably across both real-world and controlled conditions.

What’s the difference between API Tests and Browser Tests?
API Tests monitor single endpoints or URLs, whereas Browser Tests monitor web business transactions or web user journeys that may involve several actions and pages. Multistep API tests are also available to chain several API requests together.
Are you able to alert on Synthetic monitors?
Yes, alerts are built in and triggered automatically when your tests fail. Datadog also integrates with your favorite collaboration/communication tools such as Slack, Pagerduty, ServiceNow, and more.
Can I view endpoint requests end-to-end?
Yes, with the out-of-the-box APM integration, you are able to tie back any synthetic tests to their corresponding back-end, code-level insights for minimal mean time to resolution.
Is there any extra charge for using private locations?
No. There are no additional costs to set up a private location. All test runs to a private location are billed just as they are to a managed location.
What counts as an API test run?
HTTP, SSL, DNS, TCP, and ICMP all fall under API test billing. Each hit being made on your endpoint counts as a single test run. If a test is set to run from 3 locations every minute, the test will count as 180 test runs in an hour.
For multistep API tests, each step counts as an individual API test.
What counts as a browser test run?
Each simulation of a full transaction (25 steps) counts as a single test run. A single test containing 50 steps counts as 2 test runs on each execution. So, running a 51 step test (counting as 3 test runs) every 15 minutes from 5 different locations and 2 different devices means the test will count as 120 test runs in an hour.
How do browser test subtests participate in Synthetics billing?
Subtests are treated just as any other step in the browser test. Therefore, we bill a subtest as part of the overall test execution. So if a user sets up a browser test with 3 subtests, that each have 5 steps nested, that would amount to a total of 15 steps.
Is there any extra charge for enabling Synthetic RUM data collection on Browser Tests?
No. Synthetic RUM data collection comes free of charge with Synthetic Testing and Monitoring.
How is Mobile App Testing billed?
Similar to API and Browser Synthetic Testing, Mobile App Testing is billed per test run.
Is there a limit of the number of steps in a test run?
No. However Mobile App Testing does group test steps into buckets with each set of 25 steps counted as an individual test run. For example, tests with 1-25 steps will count as 1 run, tests with 25-50 will count as 2 runs, tests with 51-75 will count as 3 runs and so on.
How are test runs calculated in Mobile App Testing?
To calculate test runs take the number of buckets (sets of 25 steps) you have in your test and multiply this by the number of devices you have selected for your test. For example, if you have a test with 26 steps and 2 devices selected this will count as 4 test runs (2 sets of 25 steps * 2 devices) and if you run this test on an hourly basis this will come out to 96 test runs per day (2 sets of 25 steps * 2 devices * 24 hours).
Does Mobile App Testing use real devices or emulators / virtual devices?
Mobile App Testing uses real devices, i.e. physical phones and tablets which are connected via the cloud, to provide the most realistic testing possible. With real devices we can more accurately represent the hardware, software and network conditions your actual users will face.
How does Mobile App Testing on real devices work?
We have a fleet of real devices maintained in our managed cloud infrastructure. Once you select your preferred device (iOS or Android) to test your app with, Datadog MAT connects with that real device over cloud and sets the app for the test.
What devices does Mobile App Testing support?
MAT supports the most popular devices (smartphones and tablets) across Android and iOS, including the iPhone, iPad, Samsung Galaxy, Google Pixel and more, and we are constantly increasing support for new devices and OS versions as they become available.
What data center is Mobile App Testing available in?
Datadog Mobile App Testing is currently available to all US1, US5, and EU1 customers. All app tests will be run from the AWS US West region.
How can I begin setup for Mobile App Testing?
To begin testing with MAT: (1) Upload the app you would like to test to the platform, (2) Select Mobile Application Test from the modal New Test under UX Monitoring or on the Synthetics home page, (3) Select the devices you would like to test with, (4) Record your test case and (5) execute your test! What is Continuous Testing?
Datadog
Continuous Testing
is a comprehensive toolkit in the development cycle that offers integration and end-to-end testing with codeless test setup, self-healing capability, and seamless integration with CI providers (GitHub Actions, Azure DevOps, CircleCI, GitLab, and Jenkins) and collaboration tools to help you ship high-quality features to your users quickly.
Running tests in your CI/CD pipelines today is included with your API and Browser Testing test runs, and tests will run sequentially (one after another). If you would like to increase the speed of testing in your CI/CD pipelines, you can purchase additional Parallel Testing speed (parallelization), which makes some tests run at the same time.
For example, 1 Parallel Testing additional speed offers an additional parallel slot, allowing you to run 2 tests in parallel; 2 Parallel Testing additional speed offers 2 additional parallel slots, allowing you to run 3 tests in parallel; and so on. This helps you run more tests in parallel (at the same time), and reduce the overall execution speed of your test suite.
Am I limited to a certain number of test runs based on my additional parallelization?
No. With Parallel Testing, you can run as many tests as you need in your CI/CD pipelines. Parallelization ensures you can run more of those tests at the same time, and ultimately reduce the duration of testing in your CI/CD pipelines.
For example, if you want to run 100 tests in a CI pipeline and each test takes 10 seconds to run:
WITHOUT parallelization, your tests will run sequentially and your pipeline will take roughly
17 minutes to complete.
WITH parallelization, if you purchase (for example) an additional speed of 4 Parallel Testing, your 100 tests will run over a total of 5 parallel slots, and your pipeline will now take roughly
3 minutes to complete.
Note:
In both cases, your 100 test runs will contribute to your API or Browser Testing test run quotas.
Can I reuse my Synthetic tests that I use to monitor my production environments?
Yes. With Parallel Testing, you can use the same Synthetic tests you have configured for production monitoring across all of your staging, QA, and pre-production environments. Through variable overrides and custom configuration values, you can benefit from one test throughout your entire software development lifecycle.
What are parallel tests?
Parallel tests are tests that run simultaneously in your continuous integration and delivery pipelines to ensure that you can:
Reduce pipeline duration and ship new features faster
Increase development confidence and speed of delivery
Have complete test coverage and reduce the volume of production-breaking bugs from reaching your codebase
As an example, if you needed to run 60 tests and each test took one minute to run, it would take you one hour to run those tests sequentially. However, running those tests in parallel with a parallelization value of 60, you could run all your tests at the same time and within one minute, saving you 59 minutes to tackle other business-critical tasks. That's the power of Parallel Testing.

here

How do you define a host?
A host is any physical or virtual machine that has the Datadog agent installed with Cloud Network Monitoring enabled.
How do you define an CNM flow?
A flow is a record of traffic sent and received between a source (IP:Port) and destination (IP:Port) over a five minute time period. In some cases, similar destinations are grouped into a single flow to reduce the total flow count.
Does Cloud Network Monitoring work with containers?
Yes, Datadog Cloud Network Monitoring is designed to work in containerized and highly dynamic environments. User-defined tags allow you to slice and dice network flows by almost anything, including containers, clusters, pods, and deployments.
Do I need to purchase other Datadog products to use CNM or NDM?
Having all your infrastructure, traces, logs, and network information under one roof is something we encourage for comprehensive visibility, however, it is not required. Cloud Network Monitoring requires the purchase of an Infrastructure Pro or Enterprise plan for every host that CNM is monitoring. Network Device Monitoring only requires the purchase of one or more infrastructure hosts which are used to poll devices.
How do you define a device?
A device is a physical or virtual appliance with a unique IP address that is polled using SNMP.
How do you define a NetFlow record?
NetFlow is a network protocol created by Cisco that describes the flow of traffic across network devices. We support all NetFlow versions, including jFlow, sFlow, IPFIX or standard NetFlow v5 or v9. The Datadog agent aggregates raw NetFlow data overtime to send on a regular basis (the default being 5 mins, this can be customized).
What are retention options for NetFlow Monitoring?
We offer 15, 30, 60, and 90 day retention for NetFlow records with the default retention being 30 days. Please
contact us
for additional retention durations and inquires about pricing.
Do I need to purchase other Datadog products to use CNM or NDM?
Having all your infrastructure, traces, logs, and network information under one roof is something we encourage for comprehensive visibility, however, it is not required. Cloud Network Monitoring requires the purchase of an Infrastructure Pro or Enterprise plan for every host that CNM is monitoring. Network Device Monitoring only requires the purchase of one or more infrastructure hosts which are used to poll devices.
What is the difference between a CNM flow and NetFlow Monitoring (NDM) ?
CNM infers flow data from eBPF data it collects from the Datadog agent running on a customer host. Netflow monitoring receives flow records from physical network equipment, which today are more extensive in their information than CNM flow data. CNM flow data is used to troubleshoot host, container, and other cloud software connection issues. NetFlow Monitoring records are used to troubleshoot physical network connectivity issues and perform capacity planning.
Which devices qualify and do not qualify for the wireless AP SKU?
The Wireless AP SKU is focused on wireless APs that support OOTB API integrations built by NDM, such as Cisco Meraki. Devices that don’t qualify for this SKU include:
APs monitored directly via SNMP
Cisco Meraki devices: Switches, Appliances, Wireless LAN Controllers(WLC), and Cellular Gateways
APs monitored by WLCs
How do you define a test?
A test is a combination of TCP/UDP/ICMP traceroutes and multiple probes that traverse the network from the source to the defined destination. Each test collects information about the network, such as RTT and packet loss.
Where can I run Network Path tests from?
You can run Network Path tests from anywhere you’re running the Datadog agent, including both hosts and End User Devices, as well as from Datadog’s Managed Synthetic Locations.
Can Network Path monitor internal and external services?
Yes, while Network Path can show internal VPC-to-VPC traffic, it can also point to external hostnames. This can help prove to a SaaS vendor that an outage is happening on their end or within the public internet, rather than within your network.
Is there a difference in price between running Network Path from a Datadog agent versus a Synthetic location?
No, it’s all the same price for Network Path regardless of where the test is being run from.

Where does Observability Pipelines run?
Observability Pipelines Worker
runs in your own infrastructure. It can be installed anywhere in your infrastructure with a simple configuration and Datadog API key. This allows you to make decisions and control costs before data leaves your environment. To learn more about the setup process, check out our documentation here.
What are the benefits of the per GB ingest pricing?
This is suited for organizations with volumes below 30TB/month. It is cost effective at lower volumes and easy to understand, as well as allowing you to pay based on your usage as you scale or ramp up early on.
However, your bill will increase at a linear rate as your volume increases, so if you are expecting your observability volume to balloon in the near future, the vCPU pricing may work better for your organization.
What are the benefits of the per vCPU pricing?
Per vCPU pricing is suited for volumes above 30TB/month, as it scales better especially at high volumes. In addition, the per vCPU pricing gives you predictable pricing year round if you expect frequent spikes or changes to your organization’s volume of observability data. Finally, it allows you to scale your computational resources based on the intensity of the processing required.
How many vCPUs do I need?
Sizing and resource provisioning for Observability Pipelines Worker depends on various factors, such as the pipeline configuration and workload. Generally speaking, we recommend provisioning 1 vCPU for every 30TB/month.
Read our documentation on
Capacity Planning and Scaling
for additional details.
What happens if I send an unexpectedly high volume of data?
Committing to vCPU pricing model allows you to absorb spikes in volume.
Even if you’re paying based on ingested volume, by committing to a monthly volume of data, you are not rate-limited based on a single day’s volume. Send as much data as you need on any given day without losing visibility. Assuming your average is lower on other days, your bill is unaffected. In those cases where you have a big month, not to worry! You maintain complete visibility and may be subject to overages only on the volumes that exceed your commitment.

What is Archive Search?
Archive Search lets you run precise ad-hoc searches directly on your archived logs in cold storage within Datadog, with no rehydration required. Results stream in real time and are retained for 24 hours, up to 100K logs.
How long are search results retained?
Search results are retained for 24 hours, up to 100K logs, at no indexing cost. If you need to retain more than 100K results or keep results for longer than 24 hours, rehydration will incur standard indexing costs (Flex or Standard).
How does Archive Search differ from Rehydration?
Archive Search streams results in real time as logs are scanned and allows you to sample queries before running a full scan. Rehydration re-indexes logs back into Datadog for full long-term access but incurs indexing costs for all results.

How is Data Observability: Jobs Monitoring for Clusters usage calculated, and how is it billed?
Data Observability: Jobs Monitoring for Clusters is billed per host, per hour. This uses an average host count per hour, by sampling the number of unique hosts instrumented every five minutes and taking an average of those samples.
Example
: Suppose we observe:
1:00-1:05 pm: 100 unique hosts
1:05-1:10 pm: 300 unique hosts
1:10-1:15 pm: 150 unique hosts
1:15-1:20 pm: 50 unique hosts
1:20-2:00 pm (last 8 intervals): 0 unique hosts
The sum of unique host counts in each five-minute interval for the hour is 100 + 300 + 150 + 50 = 600. Since there are 12 five-minute intervals in one hour, we would then divide this sum by 12 to get the average, leading to 600 / 12 = 50.
Assume we see this usage pattern once a day for 30 days. This would result in a monthly total of 50 x 30 = 1,500 billable Data Observability Job Host Hours.
How is usage for Data Observability: Jobs Monitoring for Orchestrators calculated, and how is it billed?
Data Observability: Jobs Monitoring for Orchestrators is billed
per job, per hour
. Usage is calculated by summing the duration of each monitored job run (in hours) across the entire month.
Example
: Suppose we observe:
Job 1, Run 1 duration: 3.4 hours
Job 2, Run 2 duration: 0.1 hours
Job 1, Run 2 duration: 5 hours
Job 2, Run 2 duration: 0.15 hours
Job 2, Run 3 duration: 0.25 hours
The sum of the hours for all the runs is 3.4 + 0.1 + 5 + 0.15 + 0.25 = 8.9. We round to the next full hour making the usage for the month 9 Data Observability Job Hours.
Does using Data Observability: Jobs Monitoring generate usage of other Datadog products?
Data Observability: Jobs Monitoring for Clusters job execution traces generate Span Ingestion and Span Indexing usage, which may lead to additional charges beyond the allotted 0.205 GB Ingested Spans and 1,370 Indexed Spans per Jobs Monitoring host, per hour.
Data Observability: Jobs Monitoring for Clusters generates container monitoring usage for jobs on Kubernetes (K8s) and there is an allotment of 10 Jobs Monitoring containers per host.
Enabling log collection (optional) when using Data Observability: Jobs Monitoring is billed via Datadog Log Management.
Do hosts monitored by Data Observability: Jobs Monitoring for Clusters also count as Infrastructure hosts?
Hosts where Jobs Monitoring is enabled do not require Infrastructure Monitoring and are not billed as Infrastructure hosts, except in the case of Spark on Kubernetes (K8s).
For Spark on Kubernetes (K8s), any node running the Datadog agent is counted as an Infrastructure host, but only nodes where Spark jobs are actively running count toward Data Observability Job Host Hours.

Data Observability: Jobs Monitoring is available in all our AP, EU, and US data centers. It is currently not available in GovCloud (US).

Common Questions
What is a monitored table?
Datadog lets you sync as many tables as you want from your warehouse or database without counting them as monitored tables. These only count as monitored tables once you add a monitor (a quality check like freshness, nullness, or row count) to a table, view, materialized view, or column.
Standard monitors
: All standard monitors — freshness, row count, nullness, uniqueness — on a given table count as just one monitored table, no matter how many you add or whether they’re applied to the table or to individual columns within it.
Custom SQL monitors
: Each unique custom SQL monitor adds one additional monitored table, on top of any standard monitor count.
Example: A table with a freshness monitor and a row count monitor (1 monitored table, since both are standard) and three custom SQL monitors (3 more) results in 4 monitored tables.
Do I have to monitor every table in my warehouse?
No, you can monitor as many or as few tables as you’d like. Most customers start with a critical subset, like business-facing tables and key dependencies, and expand coverage over time.
Is there a minimum number of monitored tables or can I start with 1?
There is no minimum, and you can start with one monitored table.
What if the number of monitored tables fluctuates throughout the month?
Datadog measures the number of monitored tables by hour, then charges based on the average number of monitored tables over the full month.
What if I have a group by monitor on a table with 100 monitored groups?
You are charged for one monitored table, even if a group-by monitor evaluates many groups on that table.
Are lineage and metadata visibility billed separately?
No, lineage, schema, and metadata syncing is included at no additional charge. You are only billed for monitored tables and any Jobs Monitoring usage.
What if I connect more integrations?
You can connect as many integrations as you’d like. You will only be charged for the number of tables you monitor, along with any charges from Jobs Monitoring.
Does column-level lineage only apply for monitored tables?
No, Datadog can sync all tables it has permission to access, so you can view column-level lineage even for tables you are not monitoring.
What if I start monitoring jobs?
When you enable Jobs Monitoring, it is billed separately from monitored tables based on the host hours or job hours Datadog observes. This usage is independent of how many data integrations you connect.
Will monitoring impact my warehouse performance or costs?
Datadog minimizes overhead by using system metadata instead of table scans whenever possible, and you can control which monitors run and how often they run to manage performance and cost impact.
Is this available in all regions?
Quality Monitoring is available in all our AP, EU, and US data centers. It is currently not available in GovCloud (US).

How do you define a committer?
A committer means an active Git committer; they are identified through their Git author email address. A committer is counted towards billing if they commit at least 3 times in a given month.
For Runtime SCA and Runtime Code Analysis (IAST) purchased as part of Code Security, how many hosts can I run on?
You can use Runtime SCA and Runtime Code Analysis (IAST) on any host with APM installed.
What counts as a billable Datadog Runtime Code Analysis (IAST) or Runtime SCA host?
Similar to Datadog APM, a Datadog Runtime Code Analysis (IAST) host and a Runtime SCA host are hosts on which Datadog Runtime Code Analysis (IAST) and/or Runtime SCA are enabled and that are actively generating spans that are being submitted to the Datadog SaaS application.

How is the Code Security Bundle billed on-demand?
The Code Security Bundle is only billed on-demand if you have overages on a contractual commitment, For example, if you have a commitment for 20 committers but usage reflects 25 committers, 5 extra committers will be billed at the on-demand bundle rate. If the Code Security Bundle is not on your contract, you will be billed the on-demand rate for each standalone product you have enabled. For example, if you don’t have the Code Security Bundle or any standalone product on your contract, but enable Static SCA, Static Code Analysis (SAST), Runtime Code Analysis (IAST), and Runtime SCA on-demand (all included in the bundle), you will be billed separately for each product at their respective on-demand rate.
How does Datadog Runtime Code Analysis (IAST) work?
Datadog Runtime Code Analysis (IAST) uses instrumentation to analyze applications in their running state, monitoring requests and their interactions with each internal layer—operating similarly to Application Performance Monitoring (APM). This instrumentation-based approach is called Interactive Application Security Testing (IAST), which identifies code-level vulnerabilities in applications based solely on application traffic, and does not require any scans or security tests, ensuring that vulnerabilities are identified and addressed as the application runs.
